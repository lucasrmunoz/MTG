`parseSpotlight` validates that `spotlight.id` is *typed* as a number but never checks it is finite:

```ts
function parseSpotlight(value: unknown): Spotlight | null {
  if (
    !isRecord(value) ||
    typeof value.id !== "number" ||        // NaN passes — NaN is a number
    typeof value.playerId !== "number" ||
    typeof value.cardId !== "string" ||
    value.cardId === ""
  ) {
    return null;
  }
  return { id: Math.trunc(value.id), playerId: value.playerId, cardId: value.cardId };
}
```

`NaN` is a `number`, so a persisted `spotlight.id: NaN` passes the type gate, and `Math.trunc(NaN)` is `NaN`, so the restored spotlight keeps a `NaN` id. `setSpotlight` then mints every subsequent call-out from that value:

```ts
return { ...game, spotlight: { id: (game.spotlight?.id ?? 0) + 1, playerId, cardId } };
```

`NaN + 1 === NaN`, so every future spotlight is also minted with `id: NaN`. The `Spotlight` doc states the id is what makes each call-out distinct so per-device dismissal works ("a device that dismissed one still shows the next"). With a permanently-`NaN` id, `NaN !== NaN` means comparisons never match — dismissal tracking and next-call-out detection misbehave for the rest of the game.

This is the spotlight-field analogue of the already-tracked NaN guards on `turn`/`nextReminderId` (fingerprint 006c4ac8) and `life`/`commanderCasts` (7723110a): a separate field on a separate parse path with no `Number.isFinite` check. **Fix:** add `!Number.isFinite(value.id)` (and ideally a `playerId` finiteness check) to the reject conditions in `parseSpotlight`, matching the guard used for the other restored numeric fields.
