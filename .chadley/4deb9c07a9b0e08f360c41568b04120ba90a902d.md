The `type` filter is validated against a case-sensitive set, but color filters are normalized to be case-insensitive — an inconsistent contract for the same endpoint.

```csharp
private static readonly FrozenSet<string> CardTypes = FrozenSet.ToFrozenSet([ "artifact", ... ]); // default = ordinal, case-sensitive
...
if (filters.Type is not null && !CardTypes.Contains(filters.Type))
    return $"Unknown card type '{filters.Type}'. ...";   // `Creature` / `LAND` -> 400
...
var badColor = filters.Colors.FirstOrDefault(letter => !ColorLetters.Contains(char.ToUpperInvariant(letter))); // case-insensitive
...
clauses.Add($"t:{filters.Type}");   // emitted verbatim, not lowercased
```

`filters.Type` is passed straight from the query string (`CardEndpoints` `Type = type`). A caller sending `?type=Creature` or `?type=LAND` gets a 400 "Unknown card type", while `?colors=W` and `?colors=w` both work because colors are upper-cased before the check (line 72) and lower-cased before emission (line 124). The `type` clause is neither normalized on validation nor on emission.

**Fix:** build `CardTypes` with `StringComparer.OrdinalIgnoreCase` and lowercase `filters.Type` before emitting the `t:` clause (matching the color handling). The same latent case-sensitivity applies to `ColorMode` and the land-trait ids.
