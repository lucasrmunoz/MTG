The home page starts a self-rescheduling poll to wait for background-loaded vendor catalogues:

```tsx
setVendors(list);
setVendorId((current) => (current === "" ? (list[0]?.id ?? "") : current));

if (list.some((vendor) => !vendor.loaded)) {
  timer = setTimeout(() => void loadVendors(), VENDOR_POLL_MS); // 10s
}
```

The comment above it explains the intent: *"Card Kingdom … is downloaded in the background and its prices appear shortly after startup. Poll until it reports loaded, then stop."* That mental model is correct for **API mode**, where `PriceRefreshService` downloads the catalogue server-side and `/api/vendors` eventually reports `loaded: true`.

But in the **Android app build** the data source is `nativeApp`, where Card Kingdom is downloaded **on demand only** — the first time the user actually selects that vendor (`ensureVendorLoaded` → `cardKingdom.ensureLoaded()`). `nativeApp.fetchVendors()` reports its state as `loaded: cardKingdom.isLoaded()`, which stays `false` until such a selection happens. Because the default selected vendor is Mana Pool (first in the list), a typical session never selects Card Kingdom, so `list.some(v => !v.loaded)` is **permanently true** and the poll reschedules every 10 seconds for the entire session.

Each tick calls `fetchVendors()` and then `setVendors(list)` with a fresh array reference, forcing a re-render of the whole page. Worse, `vendors` is a dependency of the on-demand-load effect (`useEffect(..., [vendorId, vendors, restampCachedPrices])`), so that effect also tears down and re-runs every 10s. This is a persistent, unbounded background loop on the app's main screen — unnecessary battery/CPU on a phone.

A fix should stop polling for vendors whose catalogue is loaded on demand rather than in the background — e.g. only poll while some vendor is *both* not-loaded *and* actually loading in the background, or expose a flag from `nativeApp`/`mtgApi` distinguishing "background-loading" from "on-demand".
