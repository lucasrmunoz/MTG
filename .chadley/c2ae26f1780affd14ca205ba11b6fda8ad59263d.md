`SearchCardsByNameAsync` requests results in Scryfall's **alphabetical** order (`order=name&dir=asc`), keeps only the first page (max 175 cards), then re-sorts *that page* client-side with `MatchRank` to float the exact/prefix match to the top. `TotalMatches` reports the true total.

The gap: `MatchRank` can only promote a card that is **present on the returned page**. Because the page is ordered alphabetically (not by relevance), the exact-name match can sort beyond position 175 for any term that is a substring of 175+ card names (e.g. common creature-type words). In that case the user's exact card is absent from the visible list entirely, while the count says e.g. "200+ matches" — directly contradicting the documented "closest match first" contract:

```
/// <returns>Matching cards, closest match first; empty when nothing matches.</returns>
```

This is distinct from the already-tracked word-reordering issue (scryfall.ts, fingerprint 1339d88e): that one is about `MatchRank`'s `===`/`StartsWith` failing on reordered words; this is about **single-page truncation defeating the re-rank even for correctly-ordered terms**. The identical logic exists in the frontend mirror (`searchCards` in `src/frontend/src/lib/sources/scryfall.ts`).

**Fix options:** request `order=` by relevance where possible, or issue a targeted exact-name lookup (`!"term"`) and prepend its result, so the exact match is guaranteed present regardless of pagination.
