`ManaPoolLiveSource` is a *live* price source: `CardPricingService.FetchLiveAsync` queries it synchronously (inside `Task.WhenAll`, awaited before the response is written) on the `/api/cards/search` and `/api/cards/art` hot path. Yet it is registered through the same helper as the bulk catalogue feeds, which pins the `HttpClient.Timeout` to the **10-minute** bulk-download budget.

In `AddPricing`:
```csharp
AddLiveSource<ManaPoolLiveSource>(services);   // live, per-request
AddFeed<CardKingdomFeed>(services);            // bulk, background
```
and `AddLiveSource` wires the client with the *feed* configurator:
```csharp
private static void AddLiveSource<TSource>(IServiceCollection services) ... {
    services.AddHttpClient<TSource>(ConfigureVendorClient);   // <-- same as feeds
    ...
}
private static void ConfigureVendorClient(HttpClient client) {
    client.Timeout = PriceFeedTimeout;   // TimeSpan.FromMinutes(10)
    ...
}
```
Compare the card-data client, deliberately capped at 15s:
```csharp
private static readonly TimeSpan ScryfallTimeout = TimeSpan.FromSeconds(15);
```

When Mana Pool is slow or unresponsive, the `GetAsync` in `ManaPoolLiveSource`/`PriceFeedHttp` will not abort until the 10-minute timeout fires. Because `FetchLiveAsync` awaits every live source before returning, the entire user-facing search/art request hangs for up to ten minutes and only then completes (the resulting `TaskCanceledException` is swallowed by the generic `catch` in `FetchLiveAsync`, so the card still renders — just ten minutes late).

**Fix:** register the live source with its own short, request-appropriate timeout (a few seconds, like the Scryfall client) rather than the 10-minute bulk-feed timeout, and/or bound the live lookup with a `CancellationTokenSource` linked to a short deadline. The 10-minute budget should apply only to `AddFeed` (Card Kingdom).
