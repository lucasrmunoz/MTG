`parsePlayer` validates `life` and `commanderCasts` only with `typeof x !== "number"`, which accepts `NaN` and `Infinity` (both are `number`). `commanderCasts` is then passed through `Math.max(0, commanderCasts)`, but `Math.max(0, NaN)` is `NaN`, so that does not sanitize it either. A corrupted or hand-edited save therefore restores a game whose life total renders as `NaN` and whose ±1 adjustments stay `NaN` forever.

This is the persistence-path analogue of the already-known `applyArPlayers` NaN gap, but on a completely separate code path (`parseGame`/`parsePlayer`) that has no `Number.isFinite` guard anywhere. Adding `Number.isFinite(life)` / `Number.isInteger(commanderCasts)` checks to the validation block closes it.
