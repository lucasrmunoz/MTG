## Problem

The startup vendor poll is designed for the API/web path, where Card Kingdom's catalogue loads in the background server-side and the vendor flips to `loaded: true` shortly after startup, ending the poll:

```ts
if (list.some((vendor) => !vendor.loaded)) {
  timer = setTimeout(() => void loadVendors(), VENDOR_POLL_MS); // 10s
}
```

But in the **Android app build**, Card Kingdom is loaded *on demand* — only when the user selects that vendor (`ensureVendorLoaded`). Until then `cardKingdom.isLoaded()` is `false`, so `nativeApp.fetchVendors()` always returns Card Kingdom with `loaded: false`.

Result: for any app user who never picks Card Kingdom, `loadVendors` re-runs every 10 seconds for the entire session, each time calling `setVendors(list)` with a fresh array reference. That also re-triggers the `[vendorId, vendors, restampCachedPrices]` effect every 10s. It's a perpetual timer/re-render loop waiting for an event that only a user action can produce.

## Impact

Low — wasted timers, re-renders, and effect churn every 10s indefinitely on the most common app path (no functional breakage). Worth stopping.

## Suggested fix

Only keep polling for vendors that actually load in the background. For the app build, a cached vendor that loads on-demand should not keep the poll alive — e.g. treat on-demand cached vendors as "not pending" for the purpose of the `some(!loaded)` check, or cap the number of poll attempts.
