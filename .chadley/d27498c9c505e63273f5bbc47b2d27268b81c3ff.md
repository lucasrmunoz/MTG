`applyArPlayers` merges values coming back across the native AR bridge and is explicitly documented as tamper-proof:

> *"…so a stale or malformed AR result can never corrupt the game."*

But the merge trusts that `life`/`commanderCasts` are real numbers:

```ts
return {
  ...player,
  life: Math.trunc(update.life),
  commanderCasts: Math.max(0, Math.trunc(update.commanderCasts)),
};
```

Unlike `parseGame`/`parsePlayer` (which validate every field with `typeof … === "number"` before accepting it), `applyArPlayers` performs **no validation** on the returned `ArGamePlayer` values. If the native side ever returns a player object missing `life` (or with a non-numeric value), `Math.trunc(undefined)` is `NaN`; that `NaN` is written into game state, persisted to `localStorage` via `serializeGame`, and rendered as `NaN` in the player zone. A `NaN` life also can't be restored — `JSON.stringify(NaN)` serializes to `null`, which `parsePlayer` then rejects, discarding the whole saved game on next load.

Guarding with `Number.isFinite(update.life)` (falling back to the existing `player.life`) would make the function live up to its stated contract, matching the defensive style already used in `parseGame`.
