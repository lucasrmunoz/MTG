`GetArtVersionsAsync` paginates through Scryfall's `next_page` cursors, and `GetAsync<T>` returns `null` on HTTP 404 (the XML doc for the helper states it "translat[es] every failure mode except 'not found' into a `ScryfallException`"). The loop treats a `null` result as "end of results" via `break` and returns whatever it has already accumulated.

The inline comment — `// A 404 here means the exact name matched no printings, which is an empty result.` — is only correct on **page 0**. From page 1 onward the URL is Scryfall's own `next_page` cursor, so a 404 there is not "no matches"; it is a transient upstream error or an expired/invalid cursor occurring *after* some pages were already collected. When that happens the method returns a **partial** art list with no error and no warning, so a card with (say) 300 art versions can silently surface only the first ~175 as if that were the full set.

Contrast with the `MaxArtPages` cap just above, which at least logs a warning when it stops early. A mid-pagination `null` should be distinguished from a page-0 `null` (e.g. throw/propagate, or log a warning) rather than being silently swallowed as a normal completion.
