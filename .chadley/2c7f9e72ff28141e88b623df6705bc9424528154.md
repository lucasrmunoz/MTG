## Problem

`SearchCardsByNameAsync` builds the Scryfall query with `BuildNameQuery`, which splits the term on whitespace with `RemoveEmptyEntries`, collapsing any run of spaces into word boundaries (L109-115). But the result ordering compares against a differently-normalized term:

```csharp
var cards = matches
    .Select(ScryfallCardMapper.ToCard)
    .OrderBy(card => MatchRank(card.Name, searchTerm.Trim()))   // L67 — only Trim()'d
    .ThenBy(card => card.Name, StringComparer.OrdinalIgnoreCase)
    .ToList();
```

`MatchRank` only receives `searchTerm.Trim()`, which preserves *internal* whitespace, then does exact/prefix equality against the card name:

```csharp
private static int MatchRank(string cardName, string searchTerm)
{
    if (cardName.Equals(searchTerm, StringComparison.OrdinalIgnoreCase)) return 0;
    return cardName.StartsWith(searchTerm, StringComparison.OrdinalIgnoreCase) ? 1 : 2;
}
```

So a term with a double (or leading/trailing-collapsed-into-internal) space defeats the exact-match promotion:

- Query built from `"lightning  bolt"` → `name:"lightning" name:"bolt"`, which Scryfall matches to **Lightning Bolt** (and any other card containing both words).
- Ranking compares `"Lightning Bolt".Equals("lightning  bolt")` → false, and `StartsWith` → false, so Lightning Bolt gets **rank 2** instead of rank 0.
- The exact card is then ordered only alphabetically among partial matches instead of being surfaced first — exactly the behavior the `MatchRank` XML doc says it exists to prevent (L120-123: "searching the full name of a card puts that card first").

This only bites when the term has collapsible internal whitespace *and* the search returns more than one match (a single match is auto-opened regardless of rank), which is why the impact is low.

## Suggested fix

Normalize the term's internal whitespace before passing it to `MatchRank` (e.g. join the same split words used by `BuildNameQuery` with a single space), so the ranking comparison sees the same normalized name the query was built from.
