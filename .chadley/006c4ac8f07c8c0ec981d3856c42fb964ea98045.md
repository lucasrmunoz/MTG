`parseTurnState` validates that `turn` and `nextReminderId` are *typed* as numbers but never checks they are finite:

```ts
if (
  (activePlayerId !== undefined && typeof activePlayerId !== "number") ||
  (turn !== undefined && typeof turn !== "number") ||
  (nextReminderId !== undefined && typeof nextReminderId !== "number")
) {
  return null;
}
...
turn: typeof turn === "number" ? Math.max(1, Math.trunc(turn)) : 1,
nextReminderId: Math.max(typeof nextReminderId === "number" ? nextReminderId : 1, highestId + 1),
```

`NaN` is a `number`, so a persisted `turn: NaN` (or `nextReminderId: NaN`) passes the type gate. `Math.max(1, Math.trunc(NaN))` is `NaN`, so the restored `turn` is `NaN`; `endTurn` then computes `game.turn + 1 = NaN` forever, and the turn indicator renders `NaN` permanently. Likewise a `NaN` `nextReminderId` yields `Math.max(NaN, highestId + 1) = NaN`, so `addReminder` mints reminders with `id: NaN` and never advances the counter — every new reminder collides on the same `NaN` id.

The already-known non-finite-restore proposal (`7723110`) is scoped to per-player `life`/`commanderCasts`; the turn/reminder counters are separate fields with no finiteness guard. Add an `Number.isFinite(...)` check (or reject the save) for `turn` and `nextReminderId`, matching the guard used for the player fields.
