`BroadcastAsync` fans a message out to guests **sequentially**, awaiting each send before starting the next:

```csharp
private static async Task BroadcastAsync(GameSession session, string message)
{
    foreach (var guest in session.GuestsSnapshot())
    {
        if (!await guest.TrySendTextAsync(message))   // awaited one at a time
        {
            session.RemoveGuest(guest);
        }
    }
}
```

Each `TrySendTextAsync` is bounded by the per-socket `SendTimeout` (SessionConnection, ~10s), but that only bounds *one* socket. A single guest phone whose socket has gone quiet (backgrounded, on a dead network) forces the host to block up to the full timeout on that guest before it even attempts the next one. Because the host's receive loop calls this synchronously for every `state` frame (`HandleHostMessageAsync` line 164, awaited inside the `while` loop in `RunHostAsync`), the host cannot process its own incoming frames or push further updates during that stall. With several stuck-but-not-yet-pruned guests the delays compound to tens of seconds — the whole table freezes behind one bad connection.

Note the contrast with `DetachHost`, whose comment explicitly says a broadcast "must not wait on guest sockets" and fires-and-forgets — yet the hot-path state broadcast does exactly the waiting it warns against, just serialized across peers.

**Fix:** fan out concurrently, e.g. `await Task.WhenAll(session.GuestsSnapshot().Select(async g => { if (!await g.TrySendTextAsync(message)) session.RemoveGuest(g); }))`, so total latency is bounded by one `SendTimeout` for the whole table rather than N.
