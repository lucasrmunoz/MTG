`app.UseCors(CorsPolicy)` is placed *after* `app.UseExceptionHandler()` in the pipeline:

```csharp
app.UseExceptionHandler();   // line 27
app.UseStatusCodePages();
...
app.UseCors(CorsPolicy);     // line 35
```

CORS is applied as terminal-branch middleware here — the endpoints in `CardEndpoints.cs` do not call `.RequireCors(...)`, so header injection depends entirely on the `UseCors` middleware running for the response. When `ScryfallClient` throws a `ScryfallException`, the exception propagates back up to `UseExceptionHandler`, which clears the response and writes a fresh 502 `ProblemDetails` from `ScryfallExceptionHandler`. Any `Access-Control-Allow-Origin` header the CORS middleware added on the way down is discarded with the cleared response, and because the exception handler short-circuits, the response never re-flows through CORS.

Net effect: the handler goes to real trouble to distinguish "card data provider unavailable" (502) from "card does not exist" (404), but a browser frontend on an allowed origin cannot read *any* error body — it gets a generic CORS error. This defeats the stated purpose of the custom exception handler for exactly the clients it is meant to serve.

**Fix direction:** Move `app.UseCors(CorsPolicy)` above `app.UseExceptionHandler()` (the standard, documented placement for CORS-on-errors), or attach CORS at the endpoint level via `.RequireCors(CorsPolicy)` so it applies to re-executed error responses.
