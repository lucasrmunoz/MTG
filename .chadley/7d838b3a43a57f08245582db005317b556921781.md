On the card-lookup page, several success paths never clear a previously-set error banner, so a message from an earlier failure lingers on screen even though the current action succeeded. This is inconsistent with `handleRefreshPrices`, which explicitly calls `setError(null)` on success (line 158).

**Vendor-ensure effect (lines 117–139).** When a cached vendor (e.g. Card Kingdom) is selected but not yet loaded, the effect calls `cachedVendors.ensure(vendorId)`. On failure it sets an error and falls back to a loaded vendor (lines 120–124). But when `ensure` *succeeds*, the code runs `restampCachedPrices()` / `setVendors(...)` and never clears the error:

```ts
try {
  await cachedVendors.ensure(vendorId);
} catch (err) {
  if (!cancelled) {
    setError(err instanceof Error ? err.message : "Could not load vendor prices.");
    setVendorId(vendors.find((vendor) => vendor.loaded)?.id ?? vendorId);
  }
  return;
}
// ... success path — no setError(null)
restampCachedPrices();
```

Concrete scenario: user picks Card Kingdom, the 66 MB download fails → error banner shows and selection falls back to the live vendor. User later re-selects Card Kingdom and the download now succeeds → prices load correctly, but the banner still reads "Could not load vendor prices," contradicting the visibly-working state.

**`handleViewInAr` (lines 283–302).** Unlike `handleSearch` (line 204) and `handleRandomCard` (line 248), which call `setError(null)` before running, `handleViewInAr` only sets an error on failure and never clears one on success, so a prior banner survives a successful AR launch.

**Fix:** call `setError(null)` on the ensure success path (after line 130) and at the start of `handleViewInAr`, mirroring `handleRefreshPrices`.
