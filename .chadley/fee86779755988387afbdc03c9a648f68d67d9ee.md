## Problem

When the user opens **View in AR** for a card, the printing they actually selected/are looking at (the copy most likely sitting on the table) may never be registered as an ARCore reference image, so the camera won't recognize it.

`cardAr.open` truncates the reference set:

```ts
// ar.ts
return plugin.open({
  ...options,
  printings: options.printings.slice(0, MAX_REFERENCE_IMAGES), // first 12
});
```

The caller passes every art version in **release order, oldest first**:

```ts
// app/page.tsx handleViewInAr
printings: artVersions.map((version) => ({ id: version.id, imageUrl: version.imageUrl })),
imageUrl: selectedArtUrl ?? card.imageUrl,
```

For a card with more than 12 printings (common: Lightning Bolt, Sol Ring, Counterspell, Llanowar Elves…), if the user selects a **newer** alt-art (which sorts last), that printing's index is > 12 and it is sliced out. The comment in `ar.ts` explicitly promises "the one being viewed plus the earliest art versions", but nothing enforces the "one being viewed" half — the slice just takes the first 12 by release date.

## Impact

The user views a specific printing, physically holds that same printing, opens AR, and ARCore never gets that printing's reference image, so the card on the table is not recognized. This defeats the primary purpose of the feature for exactly the printing the user cared about.

## Suggested fix

Before slicing, move the viewed printing (matched by `cardId` / `selectedArtUrl`) to the front of `printings`, or reserve a slot for it, so it always survives the `slice(0, MAX_REFERENCE_IMAGES)`. Alternatively have the caller order `artVersions` with the selected one first when building the AR payload.
