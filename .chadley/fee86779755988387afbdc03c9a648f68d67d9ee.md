`cardAr.open` caps the reference images the AR camera will recognise:

```ts
open(options: OpenCardArOptions): Promise<void> {
  return plugin.open({
    ...options,
    printings: options.printings.slice(0, MAX_REFERENCE_IMAGES), // MAX_REFERENCE_IMAGES = 12
  });
}
```

The doc comment on `MAX_REFERENCE_IMAGES` promises the set is *"the one being viewed plus the earliest art versions."* But the implementation simply keeps the first 12 entries of whatever `printings` array it is handed — it never ensures the viewed printing is among them.

The only caller, `handleViewInAr` in `page.tsx`, builds `printings` straight from `artVersions`:

```ts
printings: artVersions.map((version) => ({ id: version.id, imageUrl: version.imageUrl })),
```

`artVersions` is fetched with `order=released&dir=asc` (see `fetchArtVersions` / `GetArtVersionsAsync`), i.e. **oldest first**. So `slice(0, 12)` keeps the 12 *oldest* printings. The printing the user opened (`card.id` / `selectedArtUrl`) is passed to `open()` only as the separate `cardId`/`imageUrl` fields — documented as the *floating* card "used when no physical card has been recognised yet" — and is **not** merged into `printings`.

Consequence: for any card with more than 12 distinct arts (extremely common for Commander staples — Sol Ring, Lightning Bolt, Counterspell, etc.), if the user is looking at a newer printing (typically the copy they actually own), that printing's reference image is never registered, so the physical card on the table is not recognised. The stated guarantee ("the one being viewed plus the earliest") is not met.

Fix: ensure the viewed printing is always included — e.g. move the entry matching `cardId` to the front of `printings` before slicing (in `page.tsx` or inside `open`), so the cap drops the *least* relevant old arts rather than the one on the table.
