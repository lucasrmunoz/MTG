`cardAr.open` documents that only "the most relevant printings ride along: **the one being viewed** plus the earliest art versions" (ar.ts lines 70-74). But the implementation just takes the first 12 of whatever list the caller passes:

```ts
// src/frontend/src/lib/ar.ts
open(options: OpenCardArOptions): Promise<void> {
  return plugin.open({
    ...options,
    printings: options.printings.slice(0, MAX_REFERENCE_IMAGES), // MAX_REFERENCE_IMAGES = 12
  });
},
```

The caller in `app/page.tsx` builds that list from **all** art versions, in Scryfall order, while the printing the user actually selected is independent (`selectedArtUrl`):

```ts
// src/frontend/src/app/page.tsx (handleViewInAr)
await cardAr.open({
  cardId: card.id,
  imageUrl: selectedArtUrl ?? card.imageUrl,
  printings: artVersions.map((version) => ({ id: version.id, imageUrl: version.imageUrl })),
  keywords: card.keywords,
});
```

Many popular cards have far more than 12 printings (Lightning Bolt, Sol Ring, Counterspell, etc.). If the user scrolls the art grid, selects a later printing, and places **that** physical copy on the table, its reference image falls outside `slice(0, 12)` and is never registered with ARCore — so the exact card being viewed cannot be recognized. This directly contradicts the documented guarantee that "the one being viewed" always rides along.

A fix would move the selected/viewed printing to the front (or reserve a slot for it) before slicing, e.g. put `cardId`'s printing first, then fill the remaining slots with the earliest versions.

Note: this is distinct from the already-known issue that `open` passes `cardId: card.id` (the default printing id) rather than the selected art id — that concerns which id is floated when no card is recognized; this concerns which reference images are registered at all.
