This module was written specifically to avoid ever holding the full ~149,000-row catalogue as one object/string — the header notes that materialising every row at once "costs hundreds of megabytes — enough to crash a phone WebView," which is why parsing is streamed row-by-row via `RowScanner`. The successful-download persist path defeats exactly that goal: it calls `JSON.stringify({ fetchedAt, prices: Object.fromEntries(catalogue) })`. `Object.fromEntries(catalogue)` builds one giant plain object containing every row, and `JSON.stringify` then produces one giant string of the whole catalogue — both alive simultaneously alongside the `catalogue` Map. This reproduces the peak-memory scenario the streaming parser exists to prevent, just moved from parse time to persist time, and it runs on every refresh on the same low-memory WebView. If it OOMs, persistence is lost and the next launch re-downloads the full ~66 MB feed.

**Fix:** stream the write incrementally (e.g. write NDJSON, one row per line, or serialize entries in chunks appended to the file) so the full object/string is never resident at once, and parse the matching format in `loadFromDisk`.
