The presence count shown to the host is snapshotted under the session lock at membership-change time, then sent to the host **outside** the lock, so two concurrent guest loops can deliver their presence updates to the host out of order:

```csharp
// join (RunGuestAsync)
var (guestCount, cachedState, hostPresent) = session.AddGuest(connection); // count under lock
...
await NotifyHostAsync(session, PresenceMessage(guestCount));               // sent later, no lock

// leave (finally)
var remaining = session.RemoveGuest(connection);                          // count under lock
await NotifyHostAsync(session, PresenceMessage(remaining));               // sent later, no lock
```

`AddGuest`/`RemoveGuest` mutate membership atomically, but the captured integer is a point-in-time value transmitted asynchronously afterward. If guest A joins (captures 2) and guest B leaves (captures 1) around the same moment, and B's `PresenceMessage(1)` reaches the host socket before A's `PresenceMessage(2)`, the host ends up displaying **2** while only one guest remains. Because presence is only re-sent on the next join/leave, the wrong roster count persists until membership changes again.

**Fix:** read the authoritative count at send time inside a per-host serialization point (e.g. read `session.GuestCount` while holding the host send lock), rather than transmitting a value captured earlier at mutation time.
