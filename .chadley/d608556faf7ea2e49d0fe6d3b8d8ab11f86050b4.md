The vendor-metadata poll re-schedules itself **only** from the success path (the `setTimeout` after a successful `fetchVendors`). The `catch` branch returns without re-arming `timer`.

The comment ("page is still usable without vendor metadata") is true for the *first* call, but on any subsequent poll a single transient failure — a network blip, or the server restarting while the ~66 MB Card Kingdom catalogue is still downloading — permanently kills the polling loop. A vendor that later finishes loading its catalogue never gets its `loaded=true` reflected in the UI: the freshness label stays stuck on "loading…" and its prices stay dashes until a full page reload.

This is the opposite of the already-known "vendor poll never terminates in the Android build" issue — here the loop stops too early and never resumes. Re-arming the timer in the `catch` branch (so a failed re-poll retries rather than aborts) fixes it.
