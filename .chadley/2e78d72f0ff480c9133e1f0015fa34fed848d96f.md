The custom starting-life `<input type="number">` validates only with `Number.isFinite`, which is true for `0` and negatives, so a Commander game can be started where every player begins at `0` or below — an immediately-lost state (a player at 0 or less life has lost). Note that `createGame` deliberately clamps *player count* via `clampPlayerCount`, but `startingLife` is passed straight through with no bound.

A second, related defect: the field is controlled by `value={startingLife}` and parses with `Number(event.target.value)`. Because `Number("") === 0` and `Number.isFinite(0)` is true, clearing the field snaps the value to `0` and re-displays `0`, so a user cannot blank the field to retype a value (e.g. delete `40` to type `25`).

**Fix:** clamp the parsed value to a sensible minimum (e.g. `Math.max(1, Math.trunc(value))`) and/or allow a transient empty string in local state, committing a floor on start. `Math.trunc(NaN)` is already correctly guarded by the `isFinite` check for non-numeric input; only the lower bound is missing.
