`applyArPlayers` merges the values the native AR session returns and its doc-comment promises: *"a stale or malformed AR result can never corrupt the game."* But the merge does no runtime validation of the incoming numbers:

```ts
return {
  ...player,
  life: Math.trunc(update.life),
  commanderCasts: Math.max(0, Math.trunc(update.commanderCasts)),
};
```

`ArGamePlayer.life` is *typed* `number`, but the value actually arrives across an untyped Capacitor plugin bridge — `plugin.openGame(...)` in `src/lib/ar.ts` resolves with whatever the native `CardAr` plugin hands back; TypeScript types are erased at that boundary. If the native side returns `life` as `undefined`, a string, or `NaN`, then `Math.trunc(undefined)` / `Math.trunc("x")` is `NaN`, and `Math.max(0, NaN)` is also `NaN`.

The corruption then propagates and is *worse* than a transient bad display:
1. `life` (or `commanderCasts`) becomes `NaN` in the live game state.
2. On persistence, `serializeGame` → `JSON.stringify` turns `NaN` into `null`.
3. On the next load, `parsePlayer` requires `typeof life === "number"`; `null` is `object`, so `parsePlayer` returns `null`, `parseGame` returns `null`, and **the entire saved game is thrown away** (`// a corrupt save starts a fresh setup`).

So a single malformed AR round-trip can silently wipe an in-progress Commander game on the next reload — exactly the outcome the comment says is impossible.

**Fix:** validate before merging, mirroring the strictness `parsePlayer` already applies. For example, only accept finite numbers and otherwise keep the existing web-side value:

```ts
const life = Number.isFinite(update.life) ? Math.trunc(update.life) : player.life;
const casts = Number.isFinite(update.commanderCasts)
  ? Math.max(0, Math.trunc(update.commanderCasts))
  : player.commanderCasts;
```

This makes the documented "malformed AR result can never corrupt the game" invariant actually hold.
