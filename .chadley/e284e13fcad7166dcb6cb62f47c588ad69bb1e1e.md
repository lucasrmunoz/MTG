`applyArPlayers` is documented as the guard that makes it so "a stale or malformed AR result can never corrupt the game." It defends against unknown ids and (per the related known finding) non-finite numbers, but it assumes the returned value **is an array**:

```ts
export function applyArPlayers(game: GameState, players: readonly ArGamePlayer[]): GameState {
  const returned = new Map(players.map((player) => [player.id, player]));
  ...
}
```

The native `CardAr` bridge is explicitly untrusted ("only life and commanderCasts are trusted coming back"). If the native `openGame` implementation resolves with a result whose `players` is `undefined`/`null`/not an array (a plausible malformed/older-plugin response), `players.map(...)` throws a `TypeError`.

Crucially, the call site cannot catch it:

```ts
// src/frontend/src/app/game/page.tsx
try {
  const result = await cardAr.openGame(toArPlayers(game));
  setGame((current) =>
    current === null ? current : applyArPlayers(current, result.players),
  );
} catch (err) {
  setError(...);
}
```

`applyArPlayers` runs inside the `setGame` updater, which React invokes during its render/commit phase — **not** synchronously inside this `try`. So the `TypeError` escapes the `catch` and surfaces as an uncaught render error, blanking the game board instead of being ignored as the docs promise. (The saved game in `localStorage` survives, so a reload recovers, but the live screen crashes.)

Fix: validate `Array.isArray(result.players)` before calling, and/or make `applyArPlayers` tolerate a non-array argument by treating it as "no updates" (returning `game` unchanged), consistent with its documented contract.
