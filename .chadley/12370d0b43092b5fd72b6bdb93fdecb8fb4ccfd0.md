The `??` fallback to `http://localhost:3000` only fires when the bound value is `null`. If a deployment sets `"Cors": { "AllowedOrigins": [] }` — a plausible "clear the defaults before adding my own" edit, or a config that binds to an empty array — `Get<string[]>()` returns an empty, non-null array, so the fallback is skipped and `WithOrigins()` receives zero origins.

The result is that CORS silently rejects every browser request, with no log line and no startup error to indicate the misconfiguration. Because the failure surfaces only as opaque cross-origin errors in the browser (no server-side signal), it is hard to diagnose.

This is distinct from the already-known CORS items (the handler-ordering issue and the hardcoded-localhost fallback critique): here the localhost fallback fails to engage in exactly the situation where an operator *tried* to configure origins. Guarding with `.Length == 0` (or logging a warning when the effective origin list is empty) would surface the problem.
